# ORAT

换握笔姿势之后，我的手在板子上愿意走的那一块变了，OpenTabletDriver 里那组 area 还是旧的。大跳够不着，小跳又觉得整条手臂都在陪跑。多数时候的处理办法是硬适应：手腕别扭两周，或者把映射数字随便拧一拧，再打两把看顺不顺。等于握笔回炉，映射也跟着回炉。

ORAT 是我给这件事做的网页工具。不用猜数字，按一轮测试谱把圈点完，它用你现在的映射把落点算回板面上的毫米坐标，圈出你这只手真正在活动的那一块，再给出一组可以直接填进 OTD 的区域参数。

## 这是什么

osu! 戳泡泡用的是绝对定位：板面上的一块物理区域被线性铺到整块屏幕。握笔一变，舒适区的宽、高、位置都会变，旧区域就对不上了。

ORAT 跑在浏览器里，Vite + TypeScript + Canvas。界面按 HarmonyOS 那套深色来：主色 `#0A59F7`，胶囊按钮，毛玻璃卡片。校准逻辑不碰 DOM，算完的握笔档案存在浏览器的 `localStorage` 里。

它不改驱动，也不读你的板。你告诉它当前映射，它只负责把「屏幕上点到了哪」翻译成「笔尖在板子上的哪」，再据此推荐新区域。

## 怎么用

1. 装好 [OpenTabletDriver](https://github.com/OpenTabletDriver/OpenTabletDriver)，确认 Absolute Mode 已经能正常把板子铺到屏幕上。
2. 本地起页面：`npm install` 然后 `npm run dev`，浏览器打开终端里给的地址。建议全屏。圈不铺满屏幕，只出在中间那块 4:3 的 playfield 里，高度大约是屏幕的八成。
3. 填上你**现在正在用**的映射。两条路：
   - 手填。宽、高、中心 X、中心 Y 单位都是毫米，旋转是度数，正值顺时针。这五个数就是 OTD 区域编辑器里的 Width、Height、X、Y、Rotation。
   - 导入 `settings.json`。Windows 上一般在 `%localappdata%\OpenTabletDriver\settings.json`。页面解析第一份 Absolute 模式的 profile，读出 `Input` 区域的 `Width`、`Height`、`XPosition`、`YPosition`、`Rotation`。数位板物理尺寸不在 settings 正文里，而在数位板配置的 `Specifications.Digitizer.Width/Height`；解析时会到根对象、profile 内嵌配置，以及 `Tablets` 表里按 profile 的板子名去找。0.6.x 那种 `AbsoluteModeSettings.Tablet` 的 `X`/`Y` 也能认。JSON 坏了，或者没有 Absolute profile、缺尺寸、缺输入区域，会用中文告诉你缺哪一项。
4. 选打法。默认是 Z/X：笔尖停在圈上，按下 Z 或 X 的那一瞬间，笔尖在屏幕上的位置才算落点。按住不放不会连打。平时用笔尖直接戳的，可以改成「笔触直接点」。BPM 默认 120，能调到 90–200。圈提前一拍出现，缩到圈上的时刻对准节拍，每拍一声，每四拍一个重音。打早打晚只影响圈的颜色，位置照样记。按你平时打图的手法去打，别为了「卡准」临时换姿势。
5. 先粗调，再细调。粗调从 playfield 中心起跳，跳距一拍比一拍远（80、140、200、260、320 像素轮着来），12 到 16 个圈，看手自然能伸多远。细调把这块映射回屏幕，铺 5×5，再接 6 到 10 下 120–180 像素的小跳。圈不会跑出 playfield。Esc 中止，回到设置。
6. 看结果。推荐参数是宽、高、中心 X、中心 Y、旋转，单位毫米和度，和 OTD 同一套语义：X / Y 是区域**中心**，不是左上角。页面上的中文摘要保留两位小数，例如 `宽 60.00 mm，高 30.00 mm，X 70.00 mm，Y 35.00 mm，旋转 -12.50°`。旋转沿用你当前的角度，工具不帮你重算握笔倾斜。
7. 填回 OTD。在区域编辑器里按这五个数改，或者把导出的 JSON 片段并进 `settings.json` 里对应 profile 的 `OutputMode.Settings`。片段就是一项 `Input`，字段为 `Width`、`Height`、`XPosition`、`YPosition`、`Rotation`。改之前先复制备份。OTD 正在跑的时候，有的版本要重启或重新应用配置才会吃到文件改动。

## 原理

绝对模式下，OTD 做的是一件很直的事：笔尖在板面上的毫米坐标，平移到输入区域中心，转一个角度，再按区域宽高缩放到输出区域。正角是顺时针。底层旋转矩阵的正角其实是逆时针，所以 OTD 转的是 `-Rotation`。ORAT 假设这块输出区域铺满你正在用的屏幕、输出中心就是屏幕中心，然后把这条链反过来。

所以一次击打记下的是那一瞬间笔尖在屏幕上的位置，不是鼠标点下去的位置。这个点先看成「相对屏幕中心偏了百分之多少」，乘上当前区域的宽和高，得到相对区域中心的毫米偏移，再按这个角度逆时针转回板面（正变换是顺时针，逆着算就反过来），加上中心坐标，就是笔尖在板子上的位置。原点在板面左上角，X 向右，Y 向下。X、Y 填的是区域中心，不是左上角。

一轮点完，落点已经是毫米坐标。舒适区用 5% 和 95% 分位数丢掉两端的手滑（线性插值，Hyndman–Fan type 7），再朝外扩 3 mm，最后夹进板面物理范围。少于 4 个落点不算。新映射的宽、高和中心直接取这块区域，旋转保持你填进来的那个值。

粗调问的是边界：跳距一拍比一拍远，手自然能伸到哪。细调问的是内部：这块区域里，网格和小跳你是不是都觉得顺。圈都收在 osu 的 4:3 playfield 里，不拿屏幕四个角来测。只做粗调容易把「偶尔够得着」也圈进去。

## 多套握笔档案

一套姿势存一份。档案里有名字、保存时间（ISO 8601）、当时推荐的映射，以及估出来的舒适区（`minXmm` / `maxXmm` / `minYmm` / `maxYmm`，毫米，含边界）。存在本机浏览器里，可以来回对比，比如「指握」和「腕托握」各打一轮，看哪组区域更接近你现在的手。换浏览器或清站点数据，档案就没了，工具不会上传到任何地方。

## 局限性

说清楚它测不到什么。

- 测的是**驱动映射之后**的屏幕坐标，再反解回去。映射填错了，毫米坐标就是错的。推荐值不会比你填进来的当前参数更可信。
- 你得知道当前的宽、高、中心、旋转。没有这组数，逆变换无从做起。`settings.json` 里经常没有板子的物理宽高，导入时如果三处都找不到 `Specifications.Digitizer`，会直接报缺尺寸。
- 反解假设输出区域铺满整屏、中心在屏幕中心。你在 OTD 里把输出区域缩成窗口、或者中心不在屏幕中间，结果对不上。
- 浏览器要尽量全屏，而且用你实际打图的那块分辨率。地址栏和系统缩放都会改掉画布像素。
- 舒适区是轴对齐的包围盒，再套上你原来的旋转。它不帮你找一个新的倾斜角，也不建模手的弧线。离群点只靠分位数削掉一点，故意点飞的几下还是会把区域撑大。
- 笔的悬停高度、滤镜、插值插件，ORAT 一概看不到。你点下去的那个像素，就是它认为的落点。

## 本地开发

需要 Node.js。常用命令：

```bash
npm install          # 安装依赖
npm run dev          # 本地开发（Vite）
npm run build        # tsc 类型检查，再 vite build
npm run preview      # 预览构建产物
npm test             # vitest 跑一遍单元测试
npm run lint         # ESLint
npm run format       # Prettier 写回
```

映射和 OTD 解析的单测在 `tests/`，改公式或 settings 解析时先跑 `npm test`。
